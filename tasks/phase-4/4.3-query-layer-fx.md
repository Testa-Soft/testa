## Goal

The shared ClickHouse access layer for every metric endpoint: parameterized
SELECTs over the daily materialized views, windowed by `experiment_id` +
`[from, to]`, with **per-currency revenue converted to the caller's
`report_currency`** via the `fx_rates` dictionary (task 1.6). Endpoints
(4.4–4.7) call these helpers and never write SQL inline.

## Context

Revenue MVs (`mv_aov_daily`, `mv_rpv_revenue_daily`) group by `currency` because
orders arrive in mixed native currencies. The read API returns a single
`report_currency`, so revenue rows must be converted and re-summed. Task 1.6
loaded a `fx_rates` ClickHouse dictionary keyed for `dictGet`. Visitor/session
MVs use Aggregating state columns (`uniqExactState`) that must be read with the
matching `-Merge` combinator.

## Acceptance criteria

- `convertedRevenueByVariation({ experimentId, from, to, reportCurrency })` →
  rows `{ variation_id, revenue, orders }` where `revenue` is summed **after**
  `dictGet('fx_rates', 'rate', (currency, day))` conversion to `reportCurrency`.
- `visitorsByVariation(...)` reads `uniqExactMerge(visitors)` from
  `mv_rpv_visitors_daily` (or `mv_experiment_summary`).
- `sessionsByVariation(...)` reads `uniqExactMerge`/`countMerge` state columns
  from `mv_sessions_daily` (sessions, sessions_with_pageview, page_views).
- `perOrderValues(...)` / `perVisitorRevenue(...)` return the sample arrays the
  stats module (4.2) needs (query `events` directly, `report_currency`-converted,
  for the significance inputs that the daily SummingMergeTree rollups can't give).
- All queries are **bound-parameter** (`{experiment_id:UInt64}` etc.) — never
  string-interpolated — and filter `is_bot = 0` (the MVs already do; keep it
  explicit where querying `events`).
- Missing FX rate for a `(currency, day)` → documented fallback (identity for
  the report currency itself; otherwise skip-with-warn or 1:1 — pick one and
  test it).

## Implementation notes

- Reuse `db/clickhouse.ts#query` with the params object; do not open new clients.
- Prefer reading the MVs for aggregate revenue/orders/visitors; hit raw `events`
  only for the per-unit sample arrays significance needs, bounded by the same
  window (cost note in a comment).
- Date window default (last 30d) is applied in 4.1's `parseMetricRequest`; this
  layer takes concrete `from`/`to`.

## Tests (live ClickHouse, `skipIf` like the collector integration suite)

- Seed `events` with two currencies + an FX dict row; assert converted revenue
  matches a hand-computed expected in `report_currency`.
- `uniqExactMerge` visitor count dedupes repeated `visitor_id`.
- Bound params: a query with a hostile `report_currency` string can't inject.

## Out of scope

- The per-metric response assembly + significance wiring (4.4–4.7).
- FX rate ingestion/refresh (task 1.6 owns it).
