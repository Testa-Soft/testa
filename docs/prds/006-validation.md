# PRD-006 — Validation flows

How we prove PRD-006 works, end to end, without a human watching each step.
Every flow below is **automated** by the harness from task 5.14 and runs with
one command:

```sh
pnpm prd006:validate          # docker CH + Redis, migrate, collector server + consumer + modeler, all flows, report
```

Output: `docs/prds/006-validation-report.md` (pass/fail per check, with
actual vs expected values) and a non-zero exit code if anything fails.

Two kinds of expected values:

- **Hand-computed fixtures** (F1): a few visitors whose correct numbers are
  written down below. These catch logic errors that an oracle written by the
  same agent could share.
- **Oracle-checked generated data** (F2, F3): a seeded generator creates
  thousands of visitors. A plain-TypeScript oracle (no SQL, written
  independently of the query code) computes the expected **daily rows** from
  the same generated data. The modeler's `metric_daily` rows must match it.

**Daily-row model (PRD Part 3).** The platform stores additive rows (§2.3);
every ratio below (CR, AOV, step rates…) is what crobot gets after **summing
the rows over the range and dividing** with the PRD §2.3 formulas. The
harness checks both: the raw rows against the goldens
(`docs/reference/samples/f1/modeled/daily_summary.json`, regenerated by
`docs/reference/samples/generate.py`) and the derived values against the
tables here. Reads go through the real sync API: subscribe → wait for
`status: ready` → `GET …/daily-summary` / `POST …/queries`.

Events enter through the real ingest path (`POST /_ingest`, HMAC-signed, like
`apps/collector/scripts/smoke-ingest.ts`) as `EnrichedEvent`s, then go through
Redis → consumer → `events_buffer` → `events`. The harness waits for the
buffer to flush (polls `count()` on `events`, 60 s timeout) before querying.
The browser half is validated separately with Playwright (V9).

## Fixture F2 — generated (oracle), "shop"

Seeded generator (`seed = 1717`): 2 experiments × 3 variations, 7 days,
≈20,000 visitors. Visitor dimensions are drawn from realistic distributions,
including **25 cities** (to exercise top-10 folding) and all channel rules.
Funnel behaviour includes repeat sessions (20% of visitors return, so `session_idx` reaches 2+), reload
duplicates (3% of purchases), upsells (15%), USD/EUR/GBP purchases, events
outside sessions (2%), contaminated visitors (0.5%) and bots (1%).

The oracle implements §2.1, §2.3, §5.1 and §5.4 directly over the generated
in-memory events (port of `generate.py` `summary_values` / `daily_summary`).

102, with **115 / 137 / 109** purchasers (one initial purchase each, value
€90). Used only for stats checks.

## After the loop: what the human tests

1. `pnpm prd006:validate` and read `docs/prds/006-validation-report.md`.
2. **Real browser smoke:** `pnpm demo`, open the demo page with a test
   experiment, walk add to cart → checkout → contact → payment → purchase via
   the helpers. Then:
   `curl -XPUT localhost:8090/api/v1/experiments/<id>/subscription -H 'X-Service-Token: …' -d '{"project_id":…,"status":"running","from":"…","report_currency":"EUR","metrics":["purchase","revenue","add_to_cart"]}'`,
   then poll `curl localhost:8090/api/v1/experiments/<id>/daily-summary -H 'X-Service-Token: …'`
   until `status` is `ready`. Your one visitor should show up.
3. **Crobot:** after the UI lands, check the results page against the
   wireframes using the F1 fixture (the harness can load F1 and leave the stack
   running: `pnpm prd006:validate --keep-up --only F1`).
